# 技术报告论证严谨性审阅

审阅对象：当前 `809fe38` 页面源码、数据和原始证据包。只读审阅，未修改网页。重点检查“数据—个案—解释—研究议程”的证据链，而非要求每个未来研究方向都先做完实验。

## 总体判断

这份报告已有足够扎实的实证核心：26 个任务上的完整能力画像、清晰的精细操作缺口，以及可以追到原始动作记录的主动观察、恢复和策略调整。结论提出 agent/端侧控制互补、能力迁移、经验工具化及 RSI，都属于合理且有启发性的研究倡议，不应因为尚未验证新系统就删掉或不断加空泛免责声明。

目前最需要修正的是三个连接处：比较所用场景版本和保留规则没有公开讲清；任务属性的强共线性没有进入正文解释；结论偶尔把“接口上合理的推断”写得像“比较实测的能力差异”。这些可通过小幅表述修正、已有日志统计及补充 provenance 解决，无需重跑整个 benchmark。

## 优先问题

### P1：公开比较的 cohort/version provenance 不完整

**位置 / 原句**：`dist/index.html:10–11`，"all 26 EBench tasks and 510 episodes"、"510 retained episodes"；`dist/research.js:15` 的统一比较表。

**证据**：原始 core 包 `archive/docs/ebench-510-completion-20260917.md:153–175` 记录 `apple_from_shelf` 场景修复后 20 个 seed 整批重跑，并以 superseded 规则替换旧批次。`evidence/main/canonical-index-original.json` 确认当前 apple000 来源为 `ebench_apple_rerun_20260917`。同一说明的 67–74 行还记录 utensils013 因 receipt-map 将动作发到错误 episode 而判无效并重跑；原产物及 INVALIDATION 留存。

**为什么重要**：这不是择优指控——已有记录恰恰说明整批替换、防止两次分数择优。但读者无法从目前网页知道修复后的场景与 leaderboard 比较模型是否完全一致。场景/评分器版本不一致会影响模型归因，而不是简单的数据展示细节。

**最小改动**：在实验附录放一个脱敏 provenance 表：task / evaluated scene version / retained run / replacement reason / comparator alignment。注明 test-mini 子集名称；将“all 26 EBench tasks”改为“all 26 tasks in the EBench test-mini evaluation suite”。先核实各模型 apple 场景版本；若不同，单列该任务并附一个排除此任务的敏感性对照。保留基础设施无效判定、整任务替换规则，不公开账号/绝对服务器路径，也不把无效重跑等同于模型失败。

### P1：属性高度混杂，不能把 mobile 优势和 precision 劣势当作两个独立机制

**位置 / 原句**：`dist/narrative.js:12`，"relative strength appears when ... larger space and adjusting ... viewpoint"；`:20–22` 的 precision 解释；`dist/index.html:21` 的总体归纳。

**复算证据**：`dist/data/tasks.json` 中，4 个 High 全为 Fixed 且 Short；14 个 Low 中 13 个 Mobile、1 个 Fixed；8 个 Medium 中 6 个 Mobile、2 个 Fixed。7 个 Long 全为 Mobile。移动组无 High。因此“移动 vs 桌面”同时也是难度/接触精度组成的变化。

**这不推翻什么**：56.58% vs 20.00%、11.25% High、Long 28.10% 都是正确且有用的描述性 profile。不要因为组间不正交而否定这些结果。

**最小改动**：正文一段说明属性重叠，旁边补交叉表；把机制句改为 “The mobile subset is a relative strength in this benchmark. Its task mix is also less dominated by high-precision assembly, so the role of mobility itself must be interpreted together with the case evidence.” 需要进一步机制验证时，再对同场景 base enabled/disabled 或观察位置作配对实验。

**无需重跑可补的分层结果**（主审复核）：Medium/Mobile 为 GPT-6-Astra 48.61% vs OpenWAM 41.67%；Medium/Fixed 为 15% vs 57.5%；Low/Mobile 为 60.26% vs 68.72%。这些可丰富画像，但 n=2 的 Medium/Fixed 不能变成普遍机制结论。

### P2：结论把 precise alignment、rapid feedback、sustained contact 三件事写成同等已测量的差距

**位置 / 原句**：`dist/index.html:21`，"Its execution is less reliable when success depends on precise alignment, rapid feedback, and sustained contact"；"local controller maintains the fast feedback needed to execute safely and accurately"。

**证据强度不同**：精细操作有四任务组及全模型对照；rapid feedback 目前是 action-batch/观测接口的结构性差异，新增三例日志有 action batch 最大 2.13/6.40/4.00 仿真秒，但没有同任务 VLA/WAM 时延测量；sustained contact 是接触任务及视频的合理解释，未独立标注/统计。

**建议表述**：保留有力结论，但拆清依据：“Its clearest measured deficit is precision-sensitive completion. The logged action–observation intervals expose a further control challenge: corrections are selected between batches rather than continuously during contact.” 后接“因此低层反馈控制是一个值得验证的互补角色”，不写成已证实混合系统提高安全性。

**最小验证**：无需先上真机。按原始请求开始、响应结束、tool 开始/结束记录计算中位数/P90/P95；对齐环境控制周期与回传图像步数；如可获取基线同样记录，再报告跨系统差距。不能用 wall−sim 当纯模型 inference。

### P2：安全部分的“large corrections”目前缺少直接量化，三例安全视频不能替代这个证据

**位置 / 原句**：`dist/index.html:17`，"Qualitative observations include large translational and rotational corrections"；`:21`，"Large EEF corrections ... unsafe ... hardware"。

**已有强证据**：apple 丢失后恢复、glasses 眼镜腿突出导致关盒受阻、coffee contact correction 请求，确实支持路径安全不等于终态成功。`dist/research.js:55–57` 已合理区分实际现象与潜在现实损害，应该保留。

**缺口**：以上案例没有建立“大幅动作”的幅度、速度超限或加速度冲击。当前 `execution-timing.json` 只有三例端点差分最大角速度，尚无 joint-name/URDF/硬件限速映射。不能用这些结果推出已发生硬件损伤或已超限；但也完全不需要说“无真机试验所以不能研究安全”。

**最小验证**：从 command target 与 measured trajectory 分别取 EEF 平移、四元数最短旋转角、base 位移、关节速度/加速度；用执行配置对应的 URDF / drive / 硬件额定限速计算比值。选出一个最大事件与视频/时间步链接，正文写清是“目标跳变”还是“实际运动跳变”。小节只需一幅分布加一个实例，贡献会比重复安全提醒强很多。

### P2：采样关节速度可以发现违规，但不能据此认证全轨迹合规；当前方法说明需明确单向性

**位置 / 原句**：`dist/app.js:28`，"Consecutive velocity estimates then support acceleration analysis"、"This makes motion-limit compliance a concrete trajectory analysis"；`scripts/analyze-execution-timing.py:35–52` 端点差分。

**核查**：典型样本间隔为 8/30≈0.267 秒。当前脚本的 raw Δq/Δt 是段平均速度，且 JSON 已明确提示 angle convention 和 joint identity，计算本身没有被冒充为瞬时峰值。三例最大值约 2.321/1.889/1.902 rad/s。

**精确改法**：补一句 “A segment-average rate exceeding a correctly matched velocity limit is evidence of a violation; rates below it do not rule out within-segment peaks.” 对 acceleration 的有限差分应基于相邻段中点时刻，并称“coarse acceleration estimate”；若要验证每步限速/jerk，需要每 physics step 轨迹。URDF 速度合规本身也不等于接触力/对象安全合规，应按指标分别展示，不混成一个 safety pass。

### P2：恢复/总结“新能力”的证据存在，比较优势的分母尚未建立

**位置 / 原句**：`dist/index.html:21`，"Its distinctive strengths ... explores ... recovers ... uses experience"；`dist/narrative.js:30–35`；`dist/narrative.js:46–48`。

**正确之处**：apple006 的 call10 检查 slip、call11 退后找视角、call17 明确因先前失败改用 arm-only，再获服务端成功，是很好的可审计适应链。teacup 被干扰后重新成为目标也很有价值。正文已说 selected rollouts 不建立总体恢复频率，避免了严重的 sample/population 错误。

**仍可加强**：结论容易被读成“比 VLA/WAM 恢复更好”，而比较视频初始物体/视角并不完全相同，也未统计恢复机会数。建议将 “distinctive strengths” 换成 “particularly informative capabilities observed in the rollouts”，或者直接突出三种动作模式而不隐含总体优越性。

**最小验证**：已有日志先做一个 recovery taxonomy：failure trigger → detection → retry/strategy change → restored subgoal → final success。报告恢复机会数和成功率，而不仅 retry 数。若做模型间实验，使用一致受控扰动；否则先作为 GPT-6-Astra 单系统审计贡献即可。

### P2：知识先验和空间理解是合理解释，却不是被消融验证的原因

**位置 / 原句**：`dist/index.html:21`，"demonstrates how strong knowledge priors and spatial understanding can support ..."；`dist/narrative.js:4`，"effortlessly bypass ... bottlenecks"。

**证据**：远控器 20/20、bookmark 90% 对次优55% 强有力地支持任务表现；但目前不能把视觉定位、任务语义、示教中的操作提示、cuRobo执行能力贡献分离。ICL 本身由独立 high GPT-6-Astra 提炼出关键帧和操作描述，系统也不是仅靠原始视频的一次输入。

**建议**：引言属于作者愿景，不必写成审稿免责声明，但 “bypass bottlenecks” 应当以问题或待检验判断引入，避免与后面的真实失败冲突。结论用 “The results are consistent with strong visual and task priors ...” 或先说实测行为再解释机制。要强调数据效率，应称“one annotated historical trajectory per task”，而不是让读者以为只有一句自然语言或未加工单视频。

### P3：排名差异缺少不确定性呈现，尤其第二 vs 第三很接近

**位置**：`dist/narrative.js:8–16`；完整比较表。

**现状**：第二名是当前 snapshot 的真实描述，不需要删除。与 Qwen SR 差约 1.15pp，比与第一名的8.59pp小得多。mixed 仅两例领先已被正确披露。

**建议**：同时展示任务配对差值分布和 bootstrap interval；有同 task/seed 结果可用 paired bootstrap，不要把 510 独立同分布 Bernoulli 当作唯一统计单位。明确是“该任务集/seed集合的不确定性”，不外推所有具身任务。无须因此将展示性报告变为检验术语堆积。

## 已有强论据，建议保留并增强

1. **完整比较 + 数据口径清晰**：当前 macro SR46.73 与237/510=46.47的区分正确；整体 SR 与任务均值复算吻合。比较模型 Score 总分与已四舍五入的 task 均值有约1e-4差异，`report-SOURCE_MAP.json` 已解释取线上总分，不属于严重不一致。
2. **优势与边界同时鲜明**：remote20/20、bookmark90% 对55%；精细任务四组High11.25、OpenWAM32.5；dishwasher5%与OpenWAM90%。这些比空泛“agent更通用”更能支撑社区讨论。
3. **进展与完成区分**：273次未完全成功中188次有正Score，peg Score.6/SR20%、nut.55/10%清楚说明终态严格条件；不要把Score解释成统一物理进度百分比。
4. **可追溯恢复链**：apple006是最强故事，不仅是语言描述，还有动作改变和终态结果。可以成为结论配图的中心。
5. **ICL展示真实完整输入**：对社区复现很有价值；主cohort全ICL、额外8对实验独立呈现、POC zero-shot独立，边界目前基本正确。
6. **安全的具体化**：物体丢失、夹闭受阻、接触高度不确定都比“LLM不安全”更可研究。进一步加动作/限速统计，是从案例走向评估协议的自然增量。
7. **RSI是研究议程而非成绩**：目前结论明确 episode history 重置，提出 held-out tasks、跨base-model工具迁移作为未来检验标准，这恰当且有启发性，不必进一步削弱。

## 让结论更有社区贡献的三条具体建议

- 把“互补”落到**接口契约**：agent发目标/接触假设，低层回报primitive成功、接触异常、grasp状态；明确何时重新规划。这样比泛泛“大脑小脑结合”更能指导后续工作。
- 把“意图模仿”落到**训练样本**：goal + pre-failure state + failure diagnosis + changed strategy + outcome；关键是保留恢复策略的选择条件，而非复制动作坐标或未经验证的自述。
- 把“RSI”落到**可积累资产和验收门槛**：将一次探索提炼为可执行检查器/工具，冻结后在未见任务验证成功率、重试步数、动作风险和成本，并测试迁移到不同基础模型。这样能把Apple个案与长期研究方向真正连起来。

## 推荐修订顺序

先补 cohort/version 信息与属性交叉说明；再让结论各句对应统计或案例；随后用现有日志扩充全cohort timing/动作分布与限速比；最后才是新增控制实验。不要把“日志还没汇总成图”写成“研究不存在证据”，也不要把“可以从日志分析”写成“已经完成全部物理安全验证”。

### 三层执行清单

**需要修文 / 现有材料整理即可**：标明test-mini；补整任务场景修复替换与基础设施无效规则；交叉表说明属性共线；拆开“已测精细操作差距”和“接口导出的快速反馈挑战”；把安全目标跳变与真实运动明确区分；保留四项研究议程，不追加笼统免责段。

**可用现有数据补算，优先于新增实验**：全cohort系统wall时间和action-batch间隔分布；在请求/响应时间戳可用时分离inference/tool时间；关节与EEF位移/速度分布，匹配URDF和真实硬件限速；task-paired差值与不确定性；主统计排除版本未对齐task的敏感性对照；已有恢复轨迹事件标注。基线版本、joint map、硬件限速若不在当前本地材料中，向数据维护方索取，而不是宣布不能分析。

**可选新增实验，不能作为当前报告发布前置条件**：同场景移动开关消融；相同扰动下的跨模型恢复比较；更密接触/力记录；agent+VLA/WAM闭环系统；意图模仿迁移；跨任务工具积累与RSI。它们应出现在明确的研究问题中，不要求作者先完成这些未来系统才有资格提出方向。
