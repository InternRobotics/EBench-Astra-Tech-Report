# GPT-6-Astra / EBench 技术报告综合审阅

审阅版本：`809fe38`，2026-09-19。由三个独立 subagent 分别审阅论证严谨性、研究贡献、实验完整性，主审交叉复核数据并综合。此次只提交审阅材料，不修改网页正文或实验结果。

## 总体判断

**这份报告最有价值的定位，是一个有完整比较数据、可追溯执行证据的具身能力诊断报告。** 它已经能回答 GPT-6-Astra 在哪些任务上有竞争力、在哪些操作上掉队，以及其恢复和探索行为为什么值得研究。26 个任务的比较、真实 ICL 输入、失败与恢复轨迹，是比宏观“强模型改变机器人”叙事更有辨识度的贡献。

结论的四个方向——Agent 与端侧策略协同、能力迁移、经验工具化与 RSI、安全执行——合理且值得保留。**不需要先实现混合系统、证明 RSI 或完成真机实验，才能提出这些研究问题。** 当前优先事项是把几处机制解释与实证结果接好、补齐评测来源和执行协议，并把已有日志转化成更有用的分析。

没有发现必须推翻主结果的证据。发现的主要风险是：读者可能把任务组成差异读成独立能力因素，把传输分块读成模型反馈周期，或把特定成功案例读成已经验证的总体恢复优势。

## 最应优先处理的六个问题

### 1. 说明 canonical cohort 的来源、场景版本和替换规则

网页只写了 510 retained episodes。原始材料记录了 `apple_from_shelf` 场景修复后整任务 20 个 seed 重跑、旧批次被 supersede；另有基础设施 receipt-map 错误造成的无效运行重跑。canonical index 确认当前 apple 来自修复后的批次。

**这是可解释的维护流程，不是择优证据。** 应补一张脱敏 provenance 表：评测子集、场景／评分器版本、保留批次、无效或替换原因、与 leaderboard 比较项的版本对应关系。先确认比较模型是否使用相同修复版本；若无法对齐，再给出排除受影响任务的敏感性结果。无需因此重新评测全部任务。

来源：core 包 `archive/docs/ebench-510-completion-20260917.md` 和 `evidence/main/canonical-index-original.json`；页面位置：[Experiment Setup](../dist/index.html)。

同样需要核对 Setup 中“共享 physics horizons 和 camera-access restrictions”的范围。当前云端结果来源明确提醒：相同任务名称和聚合方式，不自动证明 seed、场景版本、输入视图、控制接口和预算全部匹配。建议为七个比较 submission 补 protocol matrix，只对已核实字段声称共享；这一补充不影响保留当前系统级 benchmark 比较。

### 2. 把执行 chunk、工具调用和模型反馈周期分开

Setup 的 “Updated observations arrive after each action chunk” 容易让人误以为每八个物理 step 就由模型重新决策。实际日志中的八步 chunk 是执行／传输分块，模型通常在整个工具调用完成后得到反馈；一个调用可以包含多个 waypoint。

建议改为：

> The execution interface advances actions in small transport chunks. The agent receives feedback when the tool call returns, after the requested waypoint sequence has executed.

这直接关系到接触纠正、实时反应和安全讨论，应该优先改。后续图中分别标注 request、response、tool execution 和 simulator step，避免把 `Δstep / 30`、policy wall time、纯模型 inference latency 混用。

### 3. 保留属性结果，但明确任务组成的混杂

按 [tasks.json](../dist/data/tasks.json) 复算：

| 任务组 | Low | Medium | High |
| --- | ---: | ---: | ---: |
| Mobile | 13 | 6 | 0 |
| Fixed | 1 | 2 | 4 |

所有 High 任务同时属于 Fixed 和 Short；所有 Long 任务属于 Mobile。因此，移动组表现更强与高精度瓶颈并非两个独立实验结论。

正文只需明确一句属性重叠，再展示此表。仍然可以坚定地说“当前 benchmark 中移动子集是相对强项，精细操作是明显短板”。若要进一步解释移动本身的收益，再做同场景允许／禁止底盘调整的配对实验。

### 4. 让“恢复能力”有机会分母和过程定义

Apple006 是当前最强案例：它连接了失败观察、额外取证、策略改变和实际结果。Teacup 的“已经完成的目标被破坏后重新成为目标”也很有价值。应强化这些行为，而不是把标题改成笼统“自主智能”。

建议将恢复拆成五个可标注事件：**发生可恢复偏差 → 检测偏差 → 改变策略 → 恢复目标状态 → 完成全任务**。分别统计可恢复机会、尝试、局部恢复、最终完成，以及耗用步数／新引入的扰动。一次失败中的十次重试不能算十次独立恢复机会。

现有日志可以先形成 GPT-6-Astra 单系统审计。若要主张相对 VLA/WAM 的总体恢复优势，再采用相同初始状态和受控扰动比较。当前非严格配对的视频仍适合作为解释性材料。

尤其需要注意：一个系统可能制造更多失误，从而拥有更多恢复机会。直接比较自然执行中的“恢复次数”甚至“失败后的恢复率”，都可能带有选择偏差。自然 rollout 评估完整系统表现，同状态注入扰动评估恢复能力，这两个问题应分别回答。

### 5. 补充执行协议，尤其 terminal hold 和运行渠道

主审与实验审阅独立复核 510 个 episode summary：**49 个有 terminal hold，共 45,540 step，其中 6 个最终成功**。运行 routes 为 108 个 API、387 个 account、15 个 API→account。

这些不自动否定任何主成绩，也不能把那六个成功直接称为“由 hold 导致”。但它们影响读者理解执行停止、环境结算、运行渠道和计时边界。建议附录报告：policy 阶段步数、hold 步数、最终服务端结果；按渠道分层做 timing。对于中途恢复的执行，明确计时是否覆盖所有阶段。

ICL provenance 也有一个需要调和的版本点：作者最新说明是独立 GPT-6-Astra `high` 制作标注；历史归档记录过 `xhigh` 标注会话。不要用旧记录推翻作者说明，也不要假设旧包自动属于新配置。应确认当前展示流程与主评测实际使用包的对应版本，把训练来源、标注模型／effort 和执行模型／effort 分栏记录。

## 结论如何更严谨，也更有启发性

引言的 “effortlessly bypass … policy composition” 比当前正文证据更强：instruction 组并未领先，POC 定量结果尚未定稿。可以保留作者期待和问题意识，把它改成“这些表现促使我们检验……”，然后由结果回答。结论中关于知识先验和空间理解的解释，也应接在可见行为之后，避免被读成已经做过组件消融的因果结论。

### 互补：从能力比较落到控制接口

最稳的实测依据是精细完成差距；反馈实时性则应接到动作批次和请求时延日志。建议把结论中的 “precise alignment, rapid feedback, and sustained contact” 拆开说明，不把三者写成已经分别完成同口径比较的属性。

下一步研究问题应具体到：**Agent 交付什么目标和接触假设？低层控制器回报哪些失败信号？何时打断执行、交还规划？** 可以比较 task-only 调度与 event-triggered 调度，记录完成率、恢复率、时延和错误累积。当前报告提出这种接口问题已经有价值，不必先实现一个新系统。

### 能力迁移：让“意图模仿”对应一种可发布的训练样本

优先考虑样本结构：`goal → pre-failure observation → diagnosis → changed strategy → execution → outcome`。最有价值的监督是“在何种状态下选择何种恢复策略”，而不是复制教师坐标或未经验证的解释。

可比较成功轨迹行为克隆、失败—恢复序列训练、带策略解释的训练，并在未见布置上测试。数据效率需要按实际采集、推理和标注成本比较；现阶段可写为值得验证的优势。

### RSI：用可冻结、可复用的产物连接当前案例与未来研究

将一次经验转为一个接触检查器、恢复 primitive、状态估计工具或适用条件明确的经验条目；冻结后，在新 seed、新组合或不同基础模型上测试。验收指标是成功率、重试消耗、执行成本和动作风险是否改善。

Apple006 支持 episode 内经验利用，提供了这个方向的起点。把 RSI 明确写成上述测试方案，比把所有反思都命名为自我进化更有说服力。

### 安全：用轨迹和约束分析支撑问题，而不是加入空泛免责声明

当前三个视频说明物体丢失、闭合受阻和接触高度不确定；它们不能单独支撑“频繁暴力运动”或已超限的量化结论。可以从现有日志补 EEF 目标位移、旋转角、实际关节变化与执行持续时间，并对齐准确的 URDF、仿真 drive 配置和硬件限速。

**正确匹配限速后，某段平均速度超过限值可以发现违规；段平均低于限值不能排除段内瞬时峰值。** 当前典型八步采样约 0.267 秒，需要区分目标跳变、实际运动与采样分辨率。速度合规、接触力和物体安全应分别评价。

| 优先级 | 工作 | 是否需要新 rollout | 能解决什么 |
| --- | --- | --- | --- |
| 发布前优先 | cohort/version 表、反馈周期说明、Score 来源统一 | 否 | 消除可比性和协议误读 |
| 发布前优先 | 属性交叉表、hold/channel 汇总 | 否 | 正确解释能力画像与计时边界 |

| 随 POC 定稿 | checkpoint、训练技能／测试组合划分、全部测试实例与结果 | 补齐记录；必要时补评测 | 支撑未见组合泛化结论 |

## 社区贡献与交付建议

最建议强化三类产物：**同一评测体系下的能力画像、失败—恢复事件数据、可复现的执行分析工具。** 已有完整 ICL 包也是重要资产，应清楚说明它来自一个训练轨迹，经独立 GPT-6-Astra 选择关键帧并附操作标注；single-shot 不是一张图或一句提示。

共享材料优先包括：脱敏运行配置和版本、canonical episode 清单、事件和视频时间点、实际演示输入、指标与 timing 计算脚本。无需公开作者随手写的 authoring prompts，也不要以模型隐含推理作为恢复成功的证据。

相关工作定位与三份独立审阅附后。其作用是将本报告贡献落到这次评测实际提供的新证据，而不是要求所有研究方向都具有概念首创性。

已有工作提供了明确的研究起点：[SayCan](https://say-can.github.io/) 和 [RPent](https://rpent.readthedocs.io/en/latest/rst_source/development/architecture.html) 涉及规划与技能协同；[Inner Monologue](https://innermonologue.github.io/) 涉及环境反馈与重规划；[ECoT](https://embodied-cot.github.io/) 涉及结构化推理监督；[Reflexion](https://arxiv.org/abs/2303.11366) 和 [Voyager](https://voyager.minedojo.org/) 涉及反馈记忆、技能积累及复用。这些来源用于校准方向已有基础，不用于替代本报告的 EBench 实证。更有辨识度的推进是：直接 EEF 执行条件下，接触失败如何被检测、何时应换策略、怎样把恢复经验转成可验证的工具和监督。
